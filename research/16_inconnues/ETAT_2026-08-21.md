# Sauvegarde de recherche — 16 champs « Non documenté »

Date : 2026-08-21
Projet : ECU MEMS Manager
Branche de travail au moment de cette sauvegarde : `ui-rebuild`

## Objet

Cette note sauvegarde uniquement l’état de compréhension atteint dans la discussion au sujet des 16 champs actuellement affichés comme « Non documenté » dans l’onglet « Toutes les données / Toutes les mesures ».

Aucune modification fonctionnelle du programme n’est décrite ni demandée ici. Le but est de conserver un point de reprise pour une recherche ultérieure.

## Conclusion importante

Les 16 champs « Non documenté » ne sont pas des valeurs absentes ou vides.

Ils sont réellement alimentés par l’ECU parce qu’ils correspondent à des octets présents dans les trames de diagnostic `0x80` ou `0x7D`.

Le logiciel les reçoit déjà et affiche leur valeur brute via les champs `uk1`, `uk2`, `uk3`, etc.

Ce qui reste inconnu n’est donc pas :

- leur existence ;
- leur position dans les trames ;
- le fait qu’ils soient alimentés par l’ECU.

Ce qui reste à déterminer est leur signification fonctionnelle exacte : compteur, état interne, temporisation, bitfield, correction, adaptation, variable intermédiaire, etc.

## Les 16 champs actuellement encore non documentés

### Trame 0x80

1. `uk1` — octet `0x0B` de la trame `0x80`
2. `uk2` — octet `0x11` de la trame `0x80`
3. `uk3` — octet `0x19` de la trame `0x80`
4. `uk4` — octet `0x1A` de la trame `0x80`
5. `uk5` — octet `0x1B` de la trame `0x80`

### Trame 0x7D

6. `uk6` — octet `0x03` de la trame `0x7D`
7. `uk7` — octet `0x10` de la trame `0x7D`
8. `uk11` — octet `0x17` de la trame `0x7D`
9. `uk12` — octet `0x18` de la trame `0x7D`
10. `uk13` — octet `0x19` de la trame `0x7D`
11. `uk14` — octet `0x1A` de la trame `0x7D`
12. `uk15` — octet `0x1B` de la trame `0x7D`
13. `uk16` — octet `0x1C` de la trame `0x7D`
14. `uk1A` — octet `0x1D` de la trame `0x7D`
15. `uk1B` — octet `0x1E` de la trame `0x7D`
16. `uk1C` — octet `0x1F` de la trame `0x7D`

## Ce qui est déjà établi sur leur chemin de données

La ROM AANMP002 contient les mécanismes et descripteurs qui construisent les réponses `0x7D` et `0x80`.

La même méthode d’analyse ROM a déjà permis de relier plusieurs valeurs connues de diagnostic à leurs variables RAM internes, par exemple :

- régime moteur → RAM `0x005E` ;
- position IAC → RAM `0x008E` ;
- correction court terme → RAM `0x00D6` ;
- avance à l’allumage → RAM `0x00DC` ;
- lambda → RAM `0x014B` ;
- batterie → RAM `0x01F5` ;
- température air admission → RAM `0x01F7` ;
- température eau → RAM `0x01F9` ;
- MAP → RAM `0x01FB` ;
- papillon → RAM `0x01FD`.

Cela montre qu’une valeur présente dans une trame de diagnostic peut être remontée vers sa source RAM interne en étudiant les descripteurs et le code ROM qui construit la trame.

## Méthode prévue pour identifier les 16 champs plus tard

Pour chaque champ encore inconnu :

1. retrouver précisément le descripteur ROM correspondant à son octet dans `0x7D` ou `0x80` ;
2. déterminer l’adresse RAM source utilisée par ce descripteur ;
3. rechercher dans toute la ROM les instructions qui écrivent dans cette adresse RAM ;
4. rechercher également les lectures de cette adresse RAM ;
5. étudier les conditions, calculs, tables et sous-routines autour de ces accès ;
6. comparer le comportement attendu avec des captures réelles ECU si nécessaire ;
7. ne renommer le champ dans le programme que lorsque sa fonction est suffisamment prouvée.

## Champs qui étaient autrefois « inconnus » mais ne doivent plus être remis dans cette liste

Certains anciens champs ont déjà été mieux identifiés et ne doivent pas être reclassés arbitrairement parmi les 16 ci-dessus :

- l’ancien `uk8` est maintenant traité comme `DTC 4` ;
- l’ancien `uk9` est utilisé comme correction / offset de régime de ralenti ;
- `uk10` n’est plus présenté comme une simple inconnue : le programme l’affiche comme trame brute `7D14-15` et l’utilise pour le calcul de l’erreur de ralenti chaud corrigée.

Rappel important pour `7D14-15` : la correction de ralenti chaud n’est pas une constante du protocole. Elle doit suivre la valeur réellement configurée dans l’onglet Réglage et ne doit pas être figée à `-3`.

## État de décision

À ce stade :

- les 16 valeurs sont bien reçues et alimentées ;
- leur emplacement dans les trames est connu ;
- leur signification fonctionnelle exacte reste à établir ;
- la ROM AANMP002 doit servir de source principale pour poursuivre leur identification ;
- aucune modification des libellés du programme ne doit être faite sans preuve supplémentaire.

## Point de reprise futur

Quand ce sujet sera repris, commencer directement par le premier des 16 champs et suivre son descripteur ROM jusqu’à son adresse RAM, puis analyser les lectures/écritures de cette RAM dans AANMP002.

Ne pas recommencer la recherche depuis zéro et ne pas confondre « valeur non documentée » avec « valeur non alimentée ».
